Always visible

One short agent prompt, a small set of skills, the message box, and one clear Continue button. The current step is a small label.

The sidebar, long step bar, separate selection-panel title, source toolbar and repeated explanations are removed from this focused view.

Only when requested

Browse skills lets the teacher add a group and exclude individual skills. 4 jobs opens the original evidence. Compare skills opens one small chart.

Previous decisions and source details sit behind the step label. The main desktop page stays within the screen.

The same four teacher decisions

Confirm search terms → Choose job groups → Choose skills → Review curriculum fit.

No new teacher stage is added for HeadHunter, O*NET or skill merging. The agent works between the existing checkpoints.

What the complete skill chooser will do
  • The main conversation shows at most five chosen or proposed skills at a time. Larger selections use a short summary and an explicit “Review all N” control; nothing is silently dropped. Proposed additions are clearly labelled and require teacher acceptance. Existing saved choices load as-is.
  • The category dialog contains all 58 current job-backed groups, with search and short pages only inside this optional chooser. The mock uses two examples and an illustrative category; it does not claim to demonstrate the complete list.
  • Selecting a category selects every current member, including other pages and filtered members. The teacher can uncheck individual skills. Reopening the chooser retains the local draft and shows mixed category state. Agent suggestions cannot reverse an explicit exclusion.
  • There is no arbitrary requirement to choose a category. A teacher can select individual skills or make the choice in conversation, with an explicit review before saving agent-proposed changes.
  • Continue saves and confirms the current selection using the existing guarded services, then requests curriculum suggestions. A failed save keeps the draft visible and gives one useful retry. It does not approve mappings or publish the course.
  • Search terms, job groups and chapter review use the same short-question pattern. Earlier messages remain accessible through history; they do not form a second long page next to the current decision. Long replies scroll within the conversation when necessary.
Evidence, merging and O*NET stay trustworthy
  • Reuse the deployed canonical groups. “Create ETL processes” and “Develop ETL/ELT processes” stay one group, with every distinct original posting link, original label and validated passage. Count a posting once even if it supports several quotations.
  • One evidence dialog groups all quotations by posting, with a unique identity for each quotation. Label external links with the saved title and employer when available; use the posting ID only as a fallback. The in-page evidence control uses a chevron; an external arrow belongs only on the original posting links. Preserve current availability and provider-data retention rules. Full descriptions are expandable.
  • Charts use the existing ECharts integration in the app. Show at most five labelled bars, one measure and one sentence of interpretation. The standalone preview uses CSS bars to illustrate the layout; it is not an ECharts integration test.
  • Keep sample job frequency separate from O*NET importance. Show the occupation and original scale. A mapped Programming rating is context for SQL, not an official SQL-specific score. Missing ETL ratings stay unavailable rather than zero. Level is not student mastery.
  • O*NET’s 394 reference candidates do not enter the job-backed skills checklist. Relevant ratings are optional context for choosing skills; job links continue to come from postings.
  • Required coverage or changed-choice decisions appear as the current short prompt, with a plain explanation and explicit teacher action. Do not silently acknowledge incomplete evidence, bypass backend review checks, or hide a blocking decision inside optional details. Optional missing O*NET context alone should not add a separate stage.
Implementation scope and acceptance

Reuse the current Swarm state, review controller, persistence and approval services. This is a presentation revision, not another extraction or graph architecture. Preserve ownership and revision guards, teacher exclusions, final approval, publication controls, student APIs, saved learning paths, learning resources and quiz-based mastery.

Acceptance requires the real 58-skill list: category selection across pages, individual exclusions, save/reload, original links and multiple quotations, meaningful partial-coverage handling, a failed-save retry, and explicit mapping approval. At 1280×720 and 1440×900, the current decision and next action must fit without main-page scrolling. Small screens and keyboard navigation must remain usable.

The preview checks exercise category/individual selection, four distinct links per example, optional charts, no-rating handling, next/back continuity, modal keyboard behavior and responsive fit. They do not establish backend persistence or full-list usability. The original preview receipt remains local; see the implementation report for current real-database verification.

Why this approach

Chosen approach: a conversation with a small visible decision and optional details. It keeps the teacher’s direct control while limiting what they must scan.

A separate screen for every category would add more clicks. Free-text chat alone would make it harder to see exactly which skills are selected. The proposed checklist keeps that choice explicit without restoring the full dashboard.

Assumption: this focused layout is for the current Swarm decision; ordinary course navigation remains available outside it. The selected SQL and ETL examples are saved teacher choices, not newly accepted recommendations.
