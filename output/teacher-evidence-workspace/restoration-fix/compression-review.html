## Resolved finding — P2: Require a complete supported encoding token before enabling gzip

- **Original location:** `backend/app/core/restoration_compression.py:40` before the follow-up fix.
- **Original observed behavior:** `Accept-Encoding: xgzip` or `Accept-Encoding: gzip2` produced `Content-Encoding: gzip` for a large restoration response. Neither header offers the supported `gzip` encoding.
- **Cause:** The explicit refusal guard fixed `gzip;q=0`, but all remaining inputs reached Starlette 0.50.0's substring check. An unsupported token containing that substring therefore opted in accidentally.
- **Original reproduction:** In `lab_tutor_workspace_backend`, loaded the test module with `runpy.run_path`, created `_response_app(Response(LARGE_JSON, media_type="application/json", headers={"Vary": "Origin"}))`, then called `_wire_request` on `/courses/42/market-demand/state` with each header. Both unsupported values returned a 184-byte gzip body from 9,691 original bytes. `br` correctly returned the original 9,691 bytes without Content-Encoding. No pytest fixtures or database operations were involved.
- **Fix reviewed:** `_GZIP_OFFERED` at current line 10 requires token boundaries; lines 34–42 route absent/unsupported offers or explicit refusals through the existing identity responder. Compression settings, exact path/method scope, middleware placement, and payload handling are unchanged.
- **Regression scope:** `test_restoration_json_stays_plain_without_gzip_support` now includes `xgzip` and `gzip2`. Both require the exact original bytes, original Content-Length, no Content-Encoding, and preserved Origin plus Accept-Encoding Vary. Existing positive gzip/q=0.5 and explicit refusal cases remain in the same test file.
- **Resolution:** Independently reran the complete affected test file after the fix: **29 passed in 0.83 seconds**, including both new cases and the real PostgreSQL-backed state route. The finding is resolved.
