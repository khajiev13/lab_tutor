IMPLEMENTATION IN PROGRESS · 10 OCTOBER 2026

Decisions and tradeoffs

These decisions keep the approved work moving. They are listed in the order recorded in the implementation ledger. This page records choices; it does not claim that all implementation or verification is complete.

#Decision and reasonTradeoff or cost if the decision needs revision
1Use the existing feature checkout

It is the approved checkout already mounted in Docker.

Changes share the current working tree, so all unrelated work must be preserved and commits must list exact paths.
2Run frontend and backend work in parallel after agreeing on contracts

The project permits separate workers with disjoint file ownership.

An interface correction may require coordinated changes on both sides.
3Use focused behavior tests for each slice, then affected integration tests

This exercises changed behavior without repeatedly running unrelated suites.

A cross-feature regression may appear at final integration rather than in an earlier slice.
4Commit only files owned by this task

The checkout contains substantial unrelated work.

The final feature history may omit unrelated improvements, intentionally.
5Include teachable communication and social skills when supported by postings

The approved scope includes communication and O*NET essential and transferable skills.

Extraction must distinguish teachable competencies from unsupported personality inferences.
6Reuse the approved Docker restart permission during the earlier engine stall

Container inspection and stopping the old previews were themselves blocked.

A restart can interrupt local containers. Old previews remain stopped until final verification; no further restart was needed in the latest retry.
7Extend cancellation work to the existing synchronous tool adapters

The original worker could continue after the surrounding task was cancelled.

Those adapters need regression coverage beyond the initial state module.
8Fail closed on authoritative state-read errors

A database error must not be treated as an absent conversation and create a new run.

A temporary database failure returns an error instead of attempting recovery with potentially incorrect state.
9Batch related frontend checks in one worker process

Imports and transforms were unusually slow under observed host contention.

A longer test timeout can delay reporting a stalled test; strict assertions and condition-based waits remain required.
10Agree on nested review fields and mutation responses before parallel UI work

Both sides need concrete types for evidence, metrics and acknowledgements.

An unforeseen existing interface may require a small DTO adaptation.
11Normalize only URL scheme, hostname and default port for fallback posting identity

Path case, query ordering and fragments can distinguish jobs.

Some duplicates may remain separate instead of distinct postings being incorrectly merged.
12Serialize short vacancy write and purge transactions with one lifecycle lock

This removes inconsistent row-lock ordering during batch writes and purges.

Durable writes serialize, while provider and model calls remain outside those transactions and may run concurrently.
13Include occupation lookup and explicit confirmation in the catalog task

They are explicit requirements of the current plan and are already consumed by the interface.

A small endpoint adaptation may be needed; this does not expand publication permissions.
14Require an existing matching active-run pointer for occupation confirmation

A delayed request must not reactivate an analysis after chat history is cleared.

The client must start an analysis before confirming occupations.
15Agree on the additive student API before backend readback is finished

This permits independent frontend implementation while approval work continues.

An incompatible existing target identity would require a scoped API and UI adaptation before acceptance.
16Persist reconciliation summaries and require explicit teacher resolution

A local before-and-after comparison cannot preserve removed or merged skill decisions after reload.

This adds optional draft fields and a small teacher interface step; it does not relax the posting requirement.
17Allow shortlist confirmation before every skill has posting support

Confirming a shortlist starts mapping; final publication remains a separate decision with a mandatory evidence check.

Mapping may be performed for a skill that cannot yet be published. Such a skill stays unavailable to students until genuine job support is verified.
18Prepare an explicit withdrawal review before withdrawing approval

A teacher action creates a current server review; the existing approval endpoint then withdraws only this analysis’s offering. Draft choices, other approvals and saved student work remain intact.

This adds a small preparation endpoint and two clearly labelled UI actions. Withdrawal can proceed even when new candidate evidence is unavailable.
19Give new career skills course-owned identities

New skills receive stable IDs and a distinct graph label. Existing book and market skills keep their identities; course-specific evidence and metrics stay on their references.

Student and resource adapters must resolve the trusted reference ID, including the new graph label, rather than relying on a shared skill name.
20Show proposed concepts in the final review

Include normalized concept names and descriptions beside each skill’s target and chapters. This closes a gap between the approved plan and the first public review payload; the server still controls the digest.

A small additive API and display change needs focused revalidation. Older responses without concepts remain supported.
21Keep demand metrics within one analysis context

Use the active approval evidence rather than a stale display cache. If several analyses support one skill, keep their metrics separate and leave the flat bank’s combined frequency unavailable; retain all supporting links.

Frequency is temporarily unavailable for a skill with several active analysis contexts. An explicit context selector could be added later; withdrawing down to one context restores that context’s metrics.
22Bind normalized extracted skills to their validated source observation

Provider tags need exact supported identity or a verified equivalent. A normalized action label may use its server-validated extraction association; sharing a word or a final label is insufficient. Final targets require the same support check.

This preserves inferred action skills but requires explicit provenance through extraction and mapping. Unverified semantic matches remain unavailable for approval.
23Apply content removal to copied evidence as well as source snapshots

A provider-content purge redacts source quotations from all new SQL and graph copies. Keep audit IDs, hashes, original posting links and permitted derived skill records; retry graph redaction explicitly if the graph is unavailable.

Audit identity remains stable, but removed source text is no longer reproducible. Graph cleanup can remain pending until a verified retry; student readback must use authoritative redacted SQL evidence.
24Keep verified existing course skills selectable

An older book or market skill remains usable while a new evidence attachment is pending or withdrawn. The server verifies its existing course relationship; new career skills still need active job evidence and completed graph publication.

The bank shows whether the existing skill is usable. The teacher’s final review separately shows the attachment’s actual publication status. Client labels cannot grant an exemption.
25Update course readiness once and preserve saved skill identities

Successful publication updates the market gate and asks for prerequisite review, including recovery through the API or command line. Repeating a successful retry preserves a later review. Prerequisite processing includes new career skills and protects every skill already linked to a durable reference.

Teachers may need to regenerate and review prerequisites explicitly. Ambiguous duplicate names remain separate whenever merging them could break saved student work.
26Keep O*NET matching separate from job proof

Attach the original occupational evidence to validated job skills with a clear matching explanation. An inferred match can add context, but cannot make a separate O*NET skill publishable by borrowing a neighboring skill’s posting.

A differently named reference may remain unavailable for approval until its own competency has validated support. The original job skill can still be published with clearly labelled O*NET context.
27Keep saved chapters stable when a teacher remaps a skill

Current career-skill mappings follow active approvals. Existing student selections retain their original chapter IDs so their questions, resources and progress stay in place. Book and legacy market mappings retain their existing behavior.

Historical graph relationships remain for saved work. Every current-discovery and saved-path reader must use the correct mapping; real graph regressions check both paths.
